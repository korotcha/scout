# Следующие шаги и проверяемые ограничения

Обновление 25.09.2026: для первого графика актуальны `docs/QUERY_DEMAND.md` и
начальный раздел `docs/handoff/MPSTATS.md`. Прямой запрос без SKU уже проверен:
36 месяцев, полное совпадение 18 месяцев эталона. Пункты ниже — исторический
план, не разрешение включать дополнительные платные отчёты. Не повторять поиск
источника и подбор артикулов, пока рабочий endpoint не показал конкретный сбой.

1. Запустить проект в новой среде: Node, зависимости, Cloudflare bindings,
   локальные миграции и доверенная аутентификация. Не начинать с переписывания UI.
2. Проверить один поисковый запрос новым MPStats-анализом. Для каждого метода
   сохранить очищенный пример реального ответа и замер лимитов до/после.
   Особенно проверить body для search/items, period/groupBy у search/by_date,
   сортировку, полноту total, fbs и доступный исторический период.
3. Проверить сохранение и повторное открытие без upstream-вызовов; продолжение
   после 403/429/таймаута; поведение после закрытия вкладки. При большом горизонте
   текущий клиентский цикл ограничен 180 шагами за запуск, дальнейшее — продолжением.
4. Добиться подтверждения временного окна frequency у MPStats. Текущий метод
   границы месяца — приближение для сопоставимости с референсом. Не возвращать
   месячное среднее или сумму без отдельного решения пользователя.
5. Подключить настоящий AI через защищённый серверный ключ. Передавать только
   сохранённые факты, покрытие/пропуски и методики. Требовать структурированный
   ответ: за/против/проверки, ссылки на показатели; сохранять дату, модель и версию
   входных данных. Не менять статус автоматически и не генерировать уверенный
   балл при отсутствии обоснованной шкалы. Сейчас отдельный AI-балл не реализован.
6. Уточнить дополнительные источники для рекламы/новинок/выкупов. До этого
   сохранять честное состояние «данных нет». Не копировать выводы референса:
   там были спорные переходы от среднего чека к марже и от числа карточек к
   невозможности входа, а также смешение пика частотности и пика заказов.
7. Live-проверка API-подбора конкурентов и создания MPStats-группы. Фильтр ≥3 млн,
   весь сезон, релевантность менеджером, ниже порога из ручного файла допустимы.
   Обрыв после создания не должен создавать вторую группу. Если ответ создания
   потерян до сохранения ID, текущая защита просит проверить группы вручную.
   Ссылка на веб-интерфейс группы не выдумывается: сохраняется apiGroupId.
8. Реальный перенос данных D1/R2 при смене хостинга — отдельно от копирования кода.
9. Неподключённый конвейер БД1 + БД2 → новый расчётный свод. Сейчас начальная
   аналитика питается историческим source-summary.json. Загрузка файла сама по
   себе не означает готовый новый свод. Не подставлять старые данные в новый месяц.
10. Потом согласовать новый дизайн. Не применять прежнюю тему автоматически.

## Известные технические долги

- Владелец задан адресом в нескольких API; нужен единый auth/roles модуль при переносе.
- Код зависит от доверенных Sites-заголовков. Публичный обычный сервер без шлюза
  требует полноценной аутентификации; прямое доверие заголовкам будет уязвимостью.
- Нет автономного фонового задания для долгого анализа, расписания обновлений
  и подтверждённого отображения остатка API-лимитов.
- «Дополнить анализ» использует сохранённую частотность; отдельное явное обновление
  устаревшего снимка в основном экране стоит доработать. Не обещать автообновление.
- Оценки рейтинга/отзывов из отчёта имеют дату загрузки; это не live-проверка WB.
- Глобальный CSS накоплен исторически. Тема упрощена без удаления структурных правил.
  Разделять CSS по компонентам можно позже, не меняя поведение таблиц.
- После выборочного API-импорта ручные наблюдения и ранее добавленные товары
  сохраняются; состав разбора может быть шире состава новой MPStats-группы.
- Исторические docs/WORKFLOW/ANALYSIS_WORKFLOW содержат ранние ограничения
  топ-10, иные статусы и старые веса. Они не являются актуальным ТЗ.
